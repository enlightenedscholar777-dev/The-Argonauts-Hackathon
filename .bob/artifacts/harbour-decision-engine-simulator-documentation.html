Harbour Decision-Engine Simulator

Draft/skeleton documentation — generated from docs/decision_engine/structure.md and inference.md

1. Purpose

This simulator is a prototype implementation of the three-level maritime harbour security architecture. It produces a working, testable codebase against which the dashboard and real sensor adapters can be developed independently.

Decision boundary: The engine receives structured observations and records, then returns a versioned DecisionPackage containing estimates, predictions, evidence, uncertainty, and recommended actions.

2. Architecture overview

Three levels

LevelResponsibilityKey output
L1 Collect & prepare Decode, validate, normalise, and store sensor observations with full provenance Timestamped, typed Observation records in the event journal
L2 Assess & recommend Track estimation, trajectory prediction, policy checks, incident FSM, optional AI enrichment, action planning, final verification Versioned DecisionPackage per track update
L3 Human decision support Format all views for the operator: situation, forecast, authorization, evidence quality, CoA card, handoff package CourseOfActionCard + HumanHandoffPackage

L2 execution order

1. KalmanTracker
→
2. TrajectoryPredictor
→
3. PolicyEngine
→
4. IncidentManager (FSM)

The numerical and policy path (steps 1–6) runs synchronously and returns a recommendation before the optional AI branch (step 7) completes. A handoff that is already required does not wait for a generated explanation.

L1 Event journal — simulator/journal/journal.py

InMemoryJournal — thread-safe, append-only, monotonic sequence numbers, duplicate-safe. replay_all() re-emits all entries flagged is_replay=True for crash recovery without duplicate handoffs. Replace with a durable NATS JetStream consumer for production.

L2 Trajectory predictor — simulator/engine/predictor/trajectory_predictor.py

Monte-Carlo rollouts (default 50 samples, 120 s horizon, 5 s steps). Each sample draws an initial state from the track's Gaussian distribution, then advances it under the constant-velocity model with small process noise. Zone intersections are reported as ZoneHit with fraction of samples, earliest hit time, and latest hit time.

L2 Action planner — simulator/engine/planner/action_planner.py

Fixed action catalog (no actions outside this list are valid):

Action IDWhen selected
watchNo current concerns
check_missionNo active mission found; contact overdue
request_fresh_obsPosition uncertainty > 30 m
verify_with_operatorUnknown identity; moderate zone hit probability
handoff_to_officerZone hit ≥ 50 % of paths; unauthorized zone entry
await_acknowledgmentIncident already with human
no_action_requiredIncident resolved

One-step value-of-information: if gathering evidence could avoid a handoff within the remaining response window, the cheaper information step is selected first.

L2 Action verifier — simulator/engine/verifier/action_verifier.py

  • Action ID must be in the catalog
  • Track must have been updated within the freshness threshold (default 120 s)
  • HANDOFF_TO_OFFICER requires at least one supporting_evidence entry
  • VERIFY_WITH_OPERATOR for an already-verified track is downgraded to watch

8. Key design principles (from structure.md)

  • A detection does not establish identity. vehicle_id is only set when cooperative telemetry or explicit verification confirms it.
  • Bearing-only observations stay bearing-only. The pipeline never synthesises a full position from a single bearing.
  • Authoritative records and unverified reports are distinguishable. Report.verification_status and ValueOrigin carry this throughout.
  • The CPU path never waits for AI. enrich_with_ai() is a separate call; the initial recommendation is already returned.
  • Every AI proposal passes the verifier gate. Stale, uncited, or catalog-violating proposals are rejected before the operator sees them.
  • Human acknowledgment is tracked explicitly. A handoff is never silently marked complete; escalation fires on deadline.
